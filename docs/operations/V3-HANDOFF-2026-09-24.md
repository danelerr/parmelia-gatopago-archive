## 2. Decisiones vigentes: no volver a discutirlas por documentos viejos

- Consumer primero. Primer recorrido monetario: **USDC en Arbitrum Sepolia**.
  No mainnet. Stellar es futuro confirmado pero no prioridad actual; no añadir
  Base, Avalanche ni otra red al próximo incremento mínimo.
- Un único proyecto frontend **Next.js en `apps/web`**, landing + Consumer/PWA
  + páginas públicas, con Tailwind. Conservar marca/UX de client y adaptar a V3;
  no sustituir funcionalidades reales por formularios que aparenten funcionar.
- Next compone presentación; Workers conservan autorización, estado económico,
  ejecución y reconciliación. Mantener frontera App/Wallet Core y Payments/Flow;
  no reescribir todo en Server Actions ni crear microservicios preventivos.
- Objetivo de dominios: `gatopago.com`, `business.gatopago.com`,
  `api.gatopago.com` y equivalentes staging. El manifiesto define RP IDs separados.
  Son configuración objetivo, no prueba de DNS/provisión/despliegue completados.
- Testnet permite corte limpio V3 sin compatibilidad de cuentas V2. Esto no es
  permiso permanente para borrar datos o ejecutar cambios remotos sin alcance.
- No reintroducir Reown/WalletConnect como solución a la wallet consumer.
  El frontend V3 no debe depender del transporte financiero V2 ni window.ethereum.
- Login de producto por Google/magic link no otorga autoridad onchain. No volver
  al OTP/Resend por iniciativa propia. No ejecutar ceremonias de passkey al abrir
  Seguridad ni enviar correos redundantes para una operación no solicitada.
- Comercialmente fees cero como intención actual; capacidad de fee y sustitución
  de paymaster no debe otorgar custodia ni obligar a cobrar por defecto.
- Separar siempre: diseñado, implementado, probado localmente, desplegado y
  validado por usuarios/fondos. Nunca usar «100 % listo» por tener tests verdes.

## 3. Autoridad contractual aprobada y realmente implementada

La decisión más reciente **reemplaza** los diseños BASIC/PROTECTED, ADMIN 2/N
obligatorio y recovery asistido que aparecen en conversaciones/documentos antiguos.

1. Una passkey inicial: **SPEND=1, ADMIN=1**. No exige segunda llave para usarla.
2. Respaldos consumer opcionales equivalentes: **1-de-N para ambas autoridades**.
   Cualquiera puede gastar y administrar, sujeto a los controles del contrato.
3. Añadir llave requiere ADMIN actual + prueba de posesión de la nueva; commit
   con autorización fresca. No se permite dejar una política sin autoridad.
4. Sin RECOVERY, guardian de GatoPago, assisted signer, reset por email/soporte
   ni veto individual por el solo hecho de ser miembro.
5. Cancelación de propuestas exige ADMIN. Con ADMIN=1, una llave comprometida
   puede administrar/cancelar; **no se vende como resistencia a una llave robada**.
6. Perder todas las credenciales implica perder acceso. GatoPago no recupera.
7. Se conservan nonces, versiones, propuestas administrativas, timelocks de upgrade,
   freeze irreversible de upgrades, validación de migración y bibliotecas enlazadas.
8. El protocolo genérico conserva quorums y ECDSA/WebAuthn/ERC-1271. Eso no equivale
   a tener una UI multisig o una salida independiente configurada para el consumidor.

Dominio: `3.0-consumer`. Layout:
`0xdcd24b64ea3d183f0c8ec0cf5f2f5a3ed15545805791416ab100c3a0ca160f49`.
Cambió ABI/encoding/storage: **no es migración compatible del candidato anterior**.
No reutilizar firmas, manifests ni pins antiguos. CREATE2 predice direcciones;
no actualiza por sí solo contratos desplegados. Identidad/implementación inicial
y la implementación actual de una cuenta son conceptos distintos.

No mostrar dirección «lista para recibir» hasta despliegue y verificación en esa
red. Depósitos contrafactuales externos todavía pueden quedar inaccesibles si
caduca la autorización y se pierde el signer inicial; no hay bypass oculto.

## 6. Cinco bloqueadores prioritarios

1. **Admisión contractual real:** manifiesto/link hashes revisados, despliegue
   testnet autorizado, simulation/bundler, WebAuthn real, patrocinio y fallback.
   Puede exigir cambios Solidity; no prometer que sólo falta desplegar.
2. **Composición de envío:** creación → preparación/firma/submit → recarga o
   respuesta perdida → consulta de operación correcta, sin duplicar envíos.
3. **Cierre económico:** evidencia de inclusión/finalidad, saldo reconciliado,
   reserva liberada con seguridad y comprobante coherente, no éxito optimista.
4. **Credenciales y soberanía:** manager de respaldos sucesivos, prueba humana
   Android/iOS, y salida usable sin GatoPago/RP domain. Ejecución directa no basta;
   no prometer exportación de private key de passkey ni recovery inexistente.
5. **Producto/entorno:** Firebase/Turnstile/proxies aislados, UI/gates globales
   regularizados y aceptación humana. Ambos ambientes siguen `unprovisioned`,
   Firebase null, wallet_enabled vacío y pins Web vacíos.

## 7. Próximo objetivo mínimo, sin expandir alcance

Sólo: **crear cuenta → enviar USDC Arbitrum Sepolia → inclusión/finalidad →
reconciliar saldo → liberar reserva → mostrar comprobante**.

- Preparar un harness local compuesto con identidad/proveedores controlados;
  no falsificar direcciones/pins del producto para «habilitar» producción.
- Conectar creación y estado verificado: no habilitar recepción antes de código,
  identidad y política comprobados.
- Una transferencia, un identificador idempotente: recargar y perder respuesta
  de submit debe recuperar la misma operación, no reservar/enviar de nuevo.
- Observar evidencia canónica; timeout no significa fallo final ni libera fondos.
- Reconciliar balance y reserva desde la evidencia; retry/reorg no duplica crédito
  ni desbloquea gasto indebidamente.
- Mostrar receipt de la operación final con red, monto, destinatario y evidencia;
  pending/error no debe verse como confirmado.
- Después validar con usuario y testnet autorizada. No añadir otra red, rediseño,
  recovery nuevo ni B2B para resolver este recorrido.

## 8. Retomar en otra PC

Prerequisitos: Git con acceso al repo, Node **24.x** (aquí 24.19.0), pnpm
**11.23.0**, Foundry **1.7.1**, Solidity **0.8.34** según foundry.toml. Python/
Slither sólo para análisis estático. No actualizar majors «para arreglar» el setup.

```sh
git clone --branch feature/v3 git@github.com:danelerr/parmelia-links.git
cd parmelia-links
git status --short
git log -1 --oneline
pnpm install --frozen-lockfile
cd contracts
forge install --no-git --shallow forge-std=foundry-rs/forge-std@rev=bf647bd6046f2f7da30d0c2bf435e5c76a780c1b openzeppelin-contracts=OpenZeppelin/openzeppelin-contracts@rev=cab19933c33c2ad1d4c7a84864a3601dddfd16f3
cd ..
pnpm check:solidity-dependencies
pnpm build:contracts
pnpm dev:web
```

Son instrucciones para la PC nueva, **no comandos ejecutados por este traspaso**.
`contracts/lib`, `node_modules` y artefactos Foundry se regeneran; shared importa
ABIs compilados, por eso construir contratos antes de tests/builds dependientes.
No ejecutar `forge build --force` simultáneamente con tests TS: borra `out` durante
el proceso. Los guards pueden necesitar `forge build --force --extra-output metadata`
si un inspect dejó artefactos ABI-only; nunca desactivar el guard para pasarlo.

`pnpm dev:web` arranca UI, **no provisiona V3 ni habilita pagos**. Para auth local,
seguir el emulador descrito en `apps/web/README.md`, sólo usuarios sintéticos
`@example.test`. No reutilizar credenciales/proyectos V2 por comodidad.
`pnpm verify:all`/`verify:ci` no se declaran verdes: scripts raíz todavía mencionan
client/dashboard y tienen que revisarse, no borrarse para ocultar errores.

Se versionan fuentes, tests, fixtures matemáticos públicos, snapshots de ABI/layout,
lockfile, scripts, docs y cambios existentes, incluidas eliminaciones pendientes.
Las claves de fixtures no son wallets operativas. No perder juntos scripts de
deploy, biblioteca/hash manifest, ABIs congelados, vectores y tests al cherry-pick.

No se fuerzan archivos ignorados: `.env*`, `.dev.vars*` reales, keystores,
credenciales CLI, backups D1, `.wrangler`, `.next`, `out`, `cache`, node_modules,
logs, capturas temporales de `output/` ni reports Slither en Temp. Las plantillas
`.example` públicas sí pueden estar en Git. Por eso clonar **no transporta sesiones,
secretos, bases locales ni todo el estado de esta PC**. Transferir secretos sólo
por un mecanismo privado separado si luego se autoriza; no pegarlos al chat/Git.

Se revisaron patrones sensibles y nombres/tamaños de archivos cambiados antes
de publicar; no sustituye un escáner completo de secretos o auditoría histórica.
